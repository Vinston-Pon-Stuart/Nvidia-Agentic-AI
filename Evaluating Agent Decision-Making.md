## In one line

Evaluating agent decision-making means scoring the **policy** — which tool it called, what it did next, when it stopped — not just whether the final answer was correct, because a correct answer can hide a bad decision policy (three wrong tool calls, 40 seconds, 12,000 tokens, then a lucky stumble into the right answer).

- Scope: the developer-side loop while building/running an agent — cheap action-level checks, judges that score whole trajectories, and self-improvement loops (self-consistency, reflection, evaluator-optimizer). Offline benchmarks, gold datasets, regression suites, CI-gated eval harnesses are Domain 3 (3.1–3.5) territory.

---

## What "decision-making" means for an agent

- At each step an agent decides: **which tool to call** (and with what arguments), **what to do next** given the observation (continue, replan, ask for help), and **when to stop** (enough info, or budget hit). Evaluating this needs the full **trajectory** — the ordered sequence of thoughts, tool calls, observations — not just the input/output pair.
- NVIDIA's NeMo Agent Toolkit encodes this as two **separate, independent** evaluator types: `ragas` evaluators score the generated answer; a dedicated **trajectory evaluator** uses "the intermediate steps generated by the workflow to evaluate the workflow trajectory," with a judge LLM taking into account "the tools available during execution," returning a 0–1 score (1.0 = "a perfect trajectory"). **Exam-relevant point:** these measure different things — an agent can score well on one and poorly on the other.

---

## Heuristic and rule-based checks

- The cheapest, fastest way to catch a bad decision — a deterministic check before/after an action, no LLM call. LangChain's guardrails split:
  - **Deterministic guardrails** — regex, keyword matching, explicit checks: "fast, predictable, cost-effective, but may miss nuanced violations."
  - **Model-based guardrails** — LLMs/classifiers with semantic understanding: "catch subtle issues that rules miss, but are slower and more expensive."
- Applied to agent actions: schema validation (does the tool call's args match the schema?), allow-lists (is this tool even permitted?), sanity bounds (is a refund amount plausible, is a file path inside the sandbox?). Run as "before agent"/"after agent"/"around tool call" middleware — cheap enough for every action, and complementary to human-in-the-loop approval for irreversible/high-stakes calls. Anthropic calls the equivalent idea a **"gate"** in prompt-chaining.
- **Trade-off:** rule-based checks can't judge whether a *reasonable* tool was chosen among valid options, or whether a plan makes sense — that's semantic judgment, needs a model.

## LLM-as-judge on trajectories

- Foundational reference: Zheng et al., ["Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena"](https://arxiv.org/abs/2306.05685) (arXiv:2306.05685, NeurIPS 2023). Strong LLM judges (GPT-4) match human preference judgments **over 80%** of the time — "the same level of agreement between humans" — making LLM-as-judge "scalable and explainable."
- **Failure modes (likely exam probe):** **position bias** (favors whichever response is seen first/second), **verbosity bias** (longer answers score higher independent of quality), **self-enhancement bias** (a judge favors outputs from a model similar to itself), plus weak reasoning on precise/quantitative tasks. **Mitigations:** swap response order and average, add reference answers, decompose multi-aspect judgments.
- NeMo Agent Toolkit's `nat eval` operationalizes this: the trajectory evaluator and `langsmith_judge` both require a configured judge LLM, support `few_shot_examples` for calibration, and default to chain-of-thought reasoning (`use_reasoning: true`) before scoring — baking in some of the MT-Bench paper's own debiasing intuition.

## Self-consistency: sampling instead of judging

- Wang et al., ["Self-Consistency Improves Chain of Thought Reasoning in Language Models"](https://arxiv.org/abs/2203.11171) (arXiv:2203.11171, ICLR 2023): replace greedy single-path decoding with sampling a **diverse set of reasoning paths**, take the **majority-vote answer**. Gains: **GSM8K +17.9%, SVAMP +11.0%, AQuA +12.2%**.
- Applied to agent decisions: sample N candidate next-actions/plans, pick the one most agents agree on. Cost scales linearly with N; **only helps when errors are not systematic** — if every sample shares the same blind spot, voting won't fix it.
- **Exam-relevant contrast:** self-consistency improves reliability by **diversifying and voting**, no explicit critique step; reflection (next) improves by **critiquing and retrying** a single trace. Different mechanisms, combinable.

---

## Reflection and self-refinement

- **Self-Refine** (Madaan et al., arXiv:2303.17651): the *same* LLM generates → critiques its own output → refines it, iterating with no additional training/human data. ~20% absolute improvement across 7 tasks — "even state-of-the-art LLMs like GPT-4 can be further improved at test time" with this simple loop.
- **Reflexion** (Shinn et al., arXiv:2303.11366): agents "verbally reflect on task feedback signals" and store that text in an **episodic memory buffer**, conditioning the next attempt — reinforcement "not by updating weights, but through linguistic feedback." Feedback can be external (scalar rewards, unit tests) or internally simulated. Reports **91% pass@1 on HumanEval**, vs. 80% GPT-4 baseline.
- Both are decision-refinement loops within/across retries, distinct from self-consistency's parallel sampling. **Shared limitation, likely exam trap: self-critique needs an external or verifiable signal to reliably improve.** A model critiquing its own reasoning with no ground truth (no test result, no tool outcome, no human feedback) can talk itself into a wrong answer as easily as fix a right one.

---

## The evaluator-optimizer loop

- Anthropic's ["Building Effective Agents"](https://www.anthropic.com/engineering/building-effective-agents) names **evaluator-optimizer**: one LLM generates, another evaluates and gives feedback, looped. Worth the extra cost "particularly effective when we have clear evaluation criteria, and when iterative refinement provides measurable value" — signs of good fit: human feedback demonstrably improves the response, and an LLM can produce that same kind of feedback.
- Examples (literary translation, multi-round search where "the evaluator decides whether further searches are warranted") both involve continuing/stopping a decision process based on explicit judgment — the "when to stop" decision from the first section.
- Using a **separate** evaluator call (vs. Self-Refine's self-judging) also mitigates self-enhancement bias, since the two roles don't share context/self-interest.

---

## Refining decisions with these signals

- Cheapest to most expensive:
  - **Better prompts/tool descriptions** — if checks or a trajectory judge repeatedly flag the same wrong-tool pattern, often just a clearer docstring or disambiguating example fixes it.
  - **Few-shot exemplars of good decisions** — `few_shot_examples` in NAT's judge evaluators doubles as steering the policy model toward similar choices.
  - **Pruning/gating bad tools** — removing a consistently-misused tool, or adding an allow-list/schema check, is often more reliable than prompting the problem away.
  - **Fine-tuning/reward models** — when prompting plateaus, judge/verifier signal becomes training data. NVIDIA's agent-RL guidance: "that reward can come from a verifier: code that scores outputs or trajectories using tests, tool execution, schema validation, simulators, reward models, LLM-as-judge review, human preference labels, or other task-specific feedback" — explicitly listing heuristics, reward models, and LLM-judges as **interchangeable reward sources** for the same RL loop (GRPO in NVIDIA's current Nemotron post-training stack). NVIDIA's Nemotron-4 340B release included **Nemotron-4-340B-Reward**, trained specifically as a scalable judge/scorer for alignment data.

---

## Trade-offs and pitfalls (exam's favorite traps)

- **LLM-judge unreliability and bias** — position, verbosity, self-enhancement bias, weak precise/quantitative judgment (MT-Bench). Mitigate with randomized order, reference answers, reasoning-before-scoring — never trust a single unblinded judge call for a high-stakes decision.
- **Reflection without ground truth doesn't reliably help** — needs an external/verifiable signal (test results, tool output, reward) or it can reinforce its own errors.
- **Overfitting to a judge / Goodhart's law** — optimizing hard against any single scoring signal teaches the agent to game it rather than genuinely improve. NVIDIA's RL guidance, nearly verbatim: "too much [reward] shaping can teach the model to optimize the checklist instead of the task" — recommends manually inspecting 50–100 reward-function outputs before trusting it, and watching every checkpoint for "reward hacking, formatting regressions... or cases where reward improves but real quality gets worse."
- **Cost of sampling and critique** — self-consistency multiplies inference calls by N; reflection adds at least one extra generation+critique pass per iteration; evaluator-optimizer doubles LLM calls per round. Weigh against just fixing the prompt or tool interface.
- **Throughline:** a heuristic check, a trajectory judge, self-consistency, and reflection are four different mechanisms answering the same question — was this a *good decision*, independent of whether the final answer happened to be correct.

## The NVIDIA angle, read critically

- NeMo Agent Toolkit packages several of these as configurable components: `trajectory` (LLM-judge over intermediate steps), `langsmith_judge` (general LLM-as-judge, few-shot calibration), and a **profiler** doing "bottleneck analysis," "concurrency spike analysis," latency/token-efficiency reporting per run. The profiler asks a genuinely different question — not "was this decision good" but "how expensive was this path" — direct evidence for this lesson's opening claim: two agents can reach the same correct answer with wildly different cost profiles, and NVIDIA treats that as first-class, not an afterthought.
- Nemotron-4-340B-Reward and NVIDIA's current agentic-RL guidance (reward models, verifiers, LLM-as-judge as interchangeable, swappable reward sources for GRPO) show the same evaluate-and-refine loop taken all the way to weight updates, not just prompt iteration.
- **Read critically:** these are engineering capabilities (documented `nat eval` config, an open-source RL stack), not evidence NVIDIA's judges/reward models are *more accurate* than any other LLM-as-judge setup — they inherit the same MT-Bench-documented biases unless explicitly mitigated, and a dedicated reward model still needs the same "compare against your own judgment on 50–100 examples" discipline NVIDIA's own guide recommends. The profiler's cost/latency metrics aren't decision-quality metrics on their own — a fast, cheap trajectory can still be badly reasoned; profiling and trajectory-judging answer different questions, both needed. (Full evaluation-pipeline machinery — datasets, benchmark suites, CI-gated regression testing — is Domain 3, not here.)

## How to think about it for the exam

| Technique | What it evaluates/improves | Mechanism | Key limitation |
|---|---|---|---|
| **Heuristic / rule-based checks** | Individual actions (schema, allow-list, bounds) | Deterministic code, no LLM call | Can't judge semantic quality or plan reasonableness |
| **LLM-as-judge on trajectories** | Whole reasoning + tool-choice path | A judge LLM scores the trajectory | Position/verbosity/self-enhancement bias; weak on precise judgments |
| **Self-consistency** | Reliability of a single-step decision | Sample N paths, majority vote | Cost scales with N; fails if errors are systematic across samples |
| **Reflection / Self-Refine / Reflexion** | The agent's own trace, iteratively | Self-critique + retry (Reflexion adds episodic memory) | Can reinforce errors without an external/verifiable signal |
| **Evaluator-optimizer loop** | Any output with clear criteria | Separate generator and evaluator LLM calls, looped | Only worth it when feedback demonstrably improves output |
| **Reward models / fine-tuning** | The policy itself, durably | Judge/verifier signal becomes training data (e.g., GRPO) | Reward hacking / Goodhart's law if the signal is gameable |

## Quick self-check

1. Why can an agent score well on final-answer accuracy but poorly on "decision-making quality"? Give a concrete example involving tool calls.
   **A:** Final-answer scoring ignores the path taken to get there. Example: an agent that calls the wrong tool three times, burns 40 seconds and 12,000 tokens, then stumbles into the right answer scores identically to one that reasoned cleanly in two steps — but is slower, costlier, and more failure-prone.
2. Name a heuristic/rule-based check and an LLM-as-judge check for the same tool call, and explain why you'd want both rather than just one.
   **A:** Heuristic: schema validation that a refund-amount argument is within a plausible numeric range. LLM-as-judge: whether calling the refund tool at all was the reasonable choice given the conversation. You need both because rule-based checks are cheap but can't judge semantic reasonableness, while judges catch semantic issues but are slower/costlier and biased.
3. What are the three biases the MT-Bench paper identifies in LLM-as-judge, and which mitigation targets which bias?
   **A:** Position bias (favors response order shown) → mitigated by swapping order and averaging. Verbosity bias (favors longer answers) → mitigated by reference answers/decomposed judgments. Self-enhancement bias (favors outputs from a similar model) → mitigated by using a separate, differently-sourced judge.
4. How does self-consistency differ mechanically from reflection (Self-Refine/Reflexion) — sampling-and-voting vs. critique-and-retry — and why does reflection need an external signal to reliably help?
   **A:** Self-consistency samples multiple diverse reasoning paths in parallel and takes a majority vote, with no critique step. Reflection critiques and retries a single trace iteratively. Reflection needs an external/verifiable signal (test result, tool output, reward) because a model critiquing itself with no ground truth can talk itself into a wrong answer as easily as fix one.
5. In NVIDIA's NeMo Agent Toolkit, what's the difference between what the `trajectory` evaluator measures and what the profiler measures, and why do you need both?
   **A:** The `trajectory` evaluator (an LLM judge) measures whether the reasoning/tool-choice path was *good*; the profiler measures how *expensive* the path was (latency, token efficiency, bottlenecks). You need both because a cheap, fast trajectory can still be badly reasoned, and a well-reasoned trajectory can still be needlessly expensive.
