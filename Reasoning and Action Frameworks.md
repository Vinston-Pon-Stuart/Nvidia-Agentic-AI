## In one line

**ReAct** = an LLM agent loop that **interleaves reasoning and tool use, one step at a time** — think, act, read the real result, think again — so the model can look things up and self-correct instead of answering in one blind guess.

---

## Why it's needed

- A plain LLM call is **one-shot, text-in / text-out** — no way to check itself, fetch fresh facts, or act in the world.
- Fine for translation or drafting an email; **breaks on multi-step tasks, up-to-date facts, or real-world actions**.
- Reasoning-and-action frameworks add a **loop** so the model can course-correct.
- **ReAct** (Yao et al., 2022) is the one the exam names — it established "interleave reasoning and acting" as the default shape of an agent.

---

## The ReAct loop (know this cold)

Repeats **Thought → Action → Observation** until the model has enough to answer:

- **Thought** — the LLM reasons: what's happening, did the last step work, what next. *(generated by the model)*
- **Action** — the agent calls a tool from a fixed set: search, calculator, code execution, custom API. *(chosen by the model)*
- **Observation** — the tool's result. **Comes from the outside world, not the model.** *(NOT generated by the model — this is the exam trap)*

**Why the external Observation matters:** it's the agent's only link to ground truth, and it's what lets ReAct catch and fix its own mistakes — e.g., a search returns an ambiguous result, and the *next Thought* reformulates the query. A plan made once upfront can't recover like that.

Short trace (from the paper):

```
Q: Elevation range of the area the eastern sector of the Colorado orogeny extends into?
Thought: search Colorado orogeny → find the eastern-sector area → find its elevation.
Action: Search[Colorado orogeny]      Observation: mountain building in Colorado...
Action: Lookup[eastern sector]        Observation: extends into the High Plains.
Action: Search[High Plains]           Observation: refers to one of two regions.  ← ambiguous
Thought: reformulate.
Action: Search[High Plains (US)]      Observation: rise from ~1,800 to 7,000 ft.
Action: Finish[1,800 to 7,000 ft]
```

## ReAct vs. its two half-cousins

- **Reason-only (chain-of-thought):** thinks step-by-step, **no tools** → closed system, drifts into confident hallucination with nothing to check against.
- **Act-only:** calls tools, **no reasoning trace** → can't decompose goals into subgoals, wanders without a plan.
- **ReAct:** interleaves both → grounded *and* planned, re-plans after every observation.

---

## What the ReAct paper actually found

- **Knowledge QA (HotpotQA, FEVER):** grounding on a Wikipedia API cuts hallucination. But it's nuanced — ReAct beats Act on both, beats CoT on FEVER, yet **loses to CoT on HotpotQA** (rigid thought/action alternation + a bad retrieval can derail it). Best result = **ReAct + CoT combined**.
- **Interactive tasks (ALFWorld, WebShop):** ReAct clearly wins — **+34% / +10% absolute success rate** over trained imitation/RL methods, with only 1–2 examples. *(the headline number)*
- **Interpretability:** the Thought steps are a readable log of *why* the agent acted.

---

## How "Action" actually happens — tool (function) calling

- A **tool** = a name + a description ("what it does, when to use it") + JSON-schema parameters.
- The tool definitions are sent to the LLM on every call (they cost tokens and latency).
- The model emits a structured call (tool name + arguments) → **your application code runs it** → the result is fed back as the **Observation**.
- So "Action" isn't magic — it's a **tool call executed by developer code**, appended to the prompt for the next turn.

## The wider reason-and-act family

| Framework | Core idea | Loop shape |
|---|---|---|
| **Chain-of-Thought** | Reason only, no tools | Think → Answer |
| **Act-only** | Tools only, no reasoning | Act → Observe → Answer |
| **ReAct** (2022) | Interleave reasoning + tool use, step by step | Thought → Action → Observation → … |
| **Reflexion** (2023) | ReAct + a memory of past failures | trial → reflect in text → retry |
| **ReWOO** (2023) | Plan all tool calls upfront, then run them | Plan → Execute → Solve |
| **Plan-and-Solve** (2023) | Decompose into subtasks before doing any | Plan → carry out steps |

**Reflexion — add a memory of failure**
- Wraps the ReAct loop: after a failed attempt, the agent **writes a self-critique into an episodic memory buffer** and reuses it on the next try.
- It's "RL without weight updates" — the policy update is a **paragraph of text**, not a gradient step.
- Result: **91% pass@1 on HumanEval vs 80%** GPT-4 baseline (works because unit tests give a clean pass/fail to reflect on).

**ReWOO & Plan-and-Solve — plan first, then act**
- Both **separate planning from execution**, fixing ReAct's weakness (every step waits on a tool round-trip and re-reads all prior history → slow, expensive).
- **ReWOO:** a Planner writes the whole plan with placeholders (`#E1`, `#E2`) → Workers run the tools → a Solver composes the answer. **5× fewer tokens, +4% on HotpotQA**, robust to a single tool failure; reasoning is separable enough to distill into a small model.
- **Plan-and-Solve:** prompting-only version ("plan the subtasks, then do them") — fixes CoT's missing-step errors.
- **Trade-off:** cheaper and cleaner, but **can't adapt if an early tool result is wrong** — no per-step replanning the way ReAct has.

---

## Trade-offs & pitfalls (ReAct)

- **Cost / latency** — every Thought is another LLM call; multi-step tasks mean many round trips.
- **Prompt-sensitive** — needs the exact Thought/Action/Observation format; brittle if mis-tuned.
- **Error propagation** — one bad Observation early can wreck the whole chain (and it's hard to debug which step).
- **Context growth** — the full history is re-sent every step (exactly what ReWOO's design avoids).
- **No parallelism** — strictly sequential; can't fire independent tool calls at once.

---

## NVIDIA angle (read critically)

NeMo Agent Toolkit ships these as swappable YAML `_type` values:

- **`react_agent`** — the ReAct loop; same limits as above (more LLM calls, prompt-sensitive, no parallelism).
- **`rewoo_agent`** — ReWOO's Plan → Execute → Solve; needs good tool descriptions upfront, can't revise mid-run.
- **`reasoning_agent`** — NVIDIA's own wrapper: plans upfront in front of *any* agent, but **does not revise the plan during execution** (so it's closer to Plan-and-Solve than ReAct). Needs a reasoning LLM that emits `<think>` tags.

**Bottom line:** these are conformant implementations of published papers + NVIDIA's tooling — **not new algorithms**.

## How to think about it for the exam

| Idea | Takeaway |
|---|---|
| ReAct's 3 steps | Thought (LLM) → Action (tool call) → Observation (**external, not LLM**) → repeat |
| Why CoT alone hallucinates | Closed system, no external check; ReAct's Observation supplies it |
| Why Act-only is weak | No reasoning trace to plan/decompose goals |
| ReAct's real results | Beats Act on HotpotQA/FEVER; beats CoT on FEVER but *lags* CoT on HotpotQA; **+34%/+10%** vs imitation/RL on ALFWorld/WebShop |
| Mechanism behind "Action" | Tool/function calling — named tool + JSON args, run by app code, result = observation |
| Reflexion adds | Verbal self-reflection in episodic memory across tries — RL-like, no weight update |
| ReWOO / Plan-and-Solve add | Plan upfront, execute, solve — trades adaptivity for token efficiency + tool-failure robustness |
| Biggest ReAct trade-offs | Latency/cost, prompt sensitivity, error propagation, growing context, no parallelism |
| NVIDIA's role | `react_agent` / `rewoo_agent` / `reasoning_agent` as configurable NIM-backed types — tooling, not a new framework |

## Quick self-check

1. Name the three repeating steps of the ReAct loop and say which one is *not* generated by the LLM — and why that matters.
   **A:** Thought → Action → Observation. The **Observation** is not LLM-generated — it comes from an external tool/environment. That external ground truth is what lets ReAct catch and correct its own errors.
2. Does ReAct beat chain-of-thought on every benchmark? What happened on HotpotQA vs FEVER, and why?
   **A:** No. It beats CoT on FEVER but **loses to CoT on HotpotQA** — its rigid thought/action alternation limits reasoning flexibility, and a bad retrieval can derail it. Best result combines ReAct + CoT.
3. What is the concrete engineering mechanism by which a ReAct agent executes an "Action"?
   **A:** **Tool / function calling** — the model emits a structured call (tool name + JSON args), your application code runs the tool, and the result is fed back as the Observation.
4. How does ReWOO's Planner/Execute/Solver differ from ReAct's loop, and what benefit (with a number) does the paper report?
   **A:** ReWOO **plans all tool calls upfront** (with `#E` placeholders), executes them, then solves — instead of replanning every step. It reports **5× token efficiency and +4% on HotpotQA**, plus tool-failure robustness.
5. What does Reflexion add on top of ReAct, and can NVIDIA's `reasoning_agent` revise its plan mid-execution the way ReAct can?
   **A:** Reflexion adds a **verbal self-reflection stored in episodic memory** to improve the next attempt (RL-like, no weight update). NVIDIA's `reasoning_agent` plans upfront and **does not** revise mid-execution — unlike ReAct.
